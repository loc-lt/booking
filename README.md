## Product

We build one **booking core** and sell **products** on top of it as subscriptions. The core is our engine; customers buy finished products and configure them, without us writing code for them.

### Products

| Product | Buyer | When |
| --- | --- | --- |
| Booking core | Our own product teams; partners via API later | First, in this repo |
| Co-working booking | Co-working operators | First product, after the December demo, in its own repo |
| Workplace / building management | Facilities and HR teams, building owners | Second product |
| Other verticals (clinics, sports courts, venues, equipment) | Various | Only after two products work |

The core is not sold on its own at first. It is proven by two reference apps and seeded demo tenants modelled on real businesses: a co-working space, a company office and a sports court. Products use released versions of the core; they never fork or copy it.

Two habits keep the core honest without a product pushing on it:

- **Seeds as proof:** every seed tenant runs on configuration alone. If one needs special code, the core is missing a capability.
- **Real rules as the backlog:** collect booking, pricing and cancellation rules from a few design-partner operators. Each must be expressible through configuration; the ones that aren't become core work.

### Customers configure, we don't code

New customers and new requirements should not need code changes. That only works inside known axes of variation; making everything configurable produces a home-made programming language nobody can use.

The rule: **configure the common, extend the rare, code the new.**

| Level | What changes | Who | Code change? |
| --- | --- | --- | --- |
| 1. Settings | Values on existing behaviour: hours, booking window, branding | Customer admin | No |
| 2. Rules | Combinations of predefined conditions and effects | Customer admin | No |
| 3. Schema extension | New resource types, custom fields, booking forms | Customer admin | No |
| 4. Extensions | Behaviour we never anticipated: webhooks, API | Customer developer or partner | No change to the core |
| 5. New capability | A new axis of variation | Us | Yes, and it becomes configurable for everyone |

### Axes of variation

1. **What** is booked: resource types, fields, capacity, site → resource hierarchy.
2. **When** it's available: hours, holidays, blackouts, buffers, slot size.
3. **Who** may book: roles, groups, eligibility rules.
4. **How** it's booked: instant or approval, duration limits, advance window, quotas.
5. **What it costs:** price plans, rates, credits, deposits, refunds.
6. **What happens after:** check-in, no-shows, notifications, automations.
7. **How it looks:** branding, language, terms, forms.

A request outside these axes is a new option on an existing axis or an extension. It becomes a new axis only when three or more customers need it.

## Glossary

| Term | Meaning |
| --- | --- |
| **Tenant** | One paying customer organisation, e.g. GreenDesk Co-working. Tenants never see each other's data. |
| **End user / member** | A person who books through a tenant's setup. |
| **Site** | A physical location of a tenant, with its own timezone and opening hours. |
| **Resource type** | A template for bookable things (desk, meeting room, phone booth), with custom fields and policies. |
| **Resource** | One bookable thing of a type, e.g. Phone Booth 1. |
| **Booking** | A claim on a resource for a time range. |
| **Pipeline** | The fixed sequence of checks a booking request goes through before it's saved. |
| **Lifecycle** | The fixed booking statuses and the only moves allowed between them. |
| **Transition** | One move in the lifecycle (confirm, check in, cancel), always run through `transition()`. |
| **Policy** | A customer setting that shapes the lifecycle: payment, approval, check-in, cancellation, no-show. |
| **Rule** | A condition and an effect evaluated in the pipeline, e.g. "guests may book at most 2 hours". |
| **Event** | A permanent record that something happened, e.g. `booking.confirmed`. |
| **Outbox** | Where events are saved together with the change, then delivered by the worker. |
| **Config version** | One saved version of a tenant's settings or rules. Bookings remember the version they were made under. |
| **Preset** | A bundle of configuration that sets up a product for a new tenant in one click. |
| **Product / vertical** | A product built on the core (co-working, workplace). Lives in its own repo, never in this one. |
| **Reference apps** | `web/apps/console` (operators configure the core) and `web/apps/member` (members book): two apps in this repo that demonstrate and test the core. |
| **Seed** | A demo tenant defined as configuration data in `seeds/`, applied through the public API. |
| **Contract** | `contracts/openapi.yaml`, the API description both sides follow. |
| **Mock mode** | A frontend app running against generated mock APIs instead of the real backend. |

## Architecture

One Flask application split into core modules, one PostgreSQL database with per-tenant row-level security, and one worker that delivers events and runs timers. On the frontend, shared packages that every product reuses, and two reference apps built from them. Everything runs in containers.

### Stack

| Area | Choice |
| --- | --- |
| Backend | Python 3.12+, Flask, modular monolith |
| Database | PostgreSQL |
| Background work | One worker using PostgreSQL as its queue (outbox and timers) |
| Frontend | React, TypeScript, Vite, shadcn/ui, TanStack Query, TanStack Router |
| API contract | One OpenAPI 3.1 file, written UI-first by Frontend |
| Client and mocks | Orval generates typed hooks, Zod schemas and MSW mocks from the contract |
| Rules | JSONLogic, evaluated in Python and in the browser |
| Auth | JWTs from our existing auth service, verified by the core |
| Analytics and errors | PostHog and Sentry, hosted |
| Code and CI | Private GitLab, GitLab CI, GitLab container and package registries |
| Demo hosting | Our physical server, Docker Compose, Caddy |
| Production hosting | AWS or Azure |

### Core modules

Each module owns its data and talks to others only through its public service.

| Module | Owns |
| --- | --- |
| Tenancy | Tenants, account settings, branding, timezone |
| Users | People, roles, groups, permissions |
| Resources | Sites, resource types, resources, custom field values |
| Availability | Hours, blackouts, slot size, buffers, free/busy search |
| Booking | Bookings, the lifecycle, booking history |
| Rules | Rule definitions, evaluation, decision traces |
| Pricing | Price plans, rates, credits (stub until after December) |
| Configuration | Versioned settings, field definitions, presets |
| Notifications | Templates per event and channel (email first) |
| Events | Outbox, delivery; later webhooks and automations |
| Analytics | Turns events into metrics |

Later: **Payments** (plugs into the lifecycle's payment hook), files and media, search.

### Repo layout

```text
booking-core/
├── CLAUDE.md                 start here
├── core/api/                 Flask app: modules/, worker/, migrations/, tests/
├── web/                      pnpm workspace: shared packages and the two apps
│   ├── packages/             shared frontend: api-client, ui, custom-fields, rules-editor, booking-ui, app-kit
│   ├── apps/
│   │   ├── console/          operators: sites, resource types, fields, rules, flows, approvals
│   │   └── member/           members: search, book, my bookings, check in, cancel
│   └── mock-server/          local stand-in API: runs the apps' shared mock data as one real server, so console and member see each other's changes before core/api exists for a feature
├── seeds/                    demo tenants as configuration data
├── contracts/openapi.yaml    the API contract
├── infra/                    Dockerfiles, Compose files, Caddyfile
├── docs/                     these docs
└── .gitlab-ci.yml            the pipeline
```

- **No product code anywhere** ([core-boundaries.md](#core-boundaries)).
- **Two apps, like a real product:** every product has an operator console and a member app, used by different people on different domains. Two consumers also expose hidden coupling in the packages, and the member app never ships console code.
- **The apps are treated like a product:** they use only package entry points and the public API. No demo-only endpoints. If they need something, it goes into a package or the API, where products get it too.
- **Seeds are configuration, never code.**
- **The console is not throwaway:** configuring types, fields, rules and flows is the same for every product, so its building blocks live in `web/packages/`.
- **`web/mock-server` is dev-only and never deployed:** it runs the exact same scenario logic as each app's in-browser MSW mocks, but as one real local server, so console and member can share data before `core/api` implements a feature. See [frontend.md](#frontend-guide)'s "Shared mock server".

### How products use the core

The core runs as a **service**: its own deployment and database. Products never run core code in their own app.

| Connection | From → to | Used for |
| --- | --- | --- |
| User's JWT | Product frontend → core API | Bookings, availability, resources, rules, config |
| User's JWT | Product frontend → product API | Product-only features: memberships, invoices |
| Service token | Product API → core API | Applying presets, creating resources, reading bookings |
| Signed webhook | Core worker → product API | Reacting to `booking.confirmed`, `booking.completed`, … |

| A product needs to… | How |
| --- | --- |
| Store product-only data | Its own backend and database; the core never sees those tables |
| Add a field to a core object | A custom field defined by its preset, never a core schema change |
| Set up a new customer | Apply its presets through the core config API |
| Do something the core can't | Request a core change in this repo; meanwhile use an event listener or its own backend |

On the frontend, a product installs the `@booking-core/*` packages from our GitLab npm registry, sets up the client with `app-kit`, overrides the theme tokens, and builds its own screens from core hooks and components. Examples: [examples/product-app/](docs/examples/product-app/).

Packages follow semantic versioning with a changelog. Breaking changes only come in a major version; each `api-client` version states which core API version it needs.

**Before the first product starts** (after December), the core needs: webhook delivery to outside subscribers with signatures and retries, service tokens with scopes, a stable `/api/v1`, and published packages and images.

## Core boundaries

The core never knows which product it is running. Code like `if product == "coworking"` or `if tenant == "GreenDesk"` turns the core into one product with extra steps. Under deadline pressure it always looks like the fastest fix, so this is the rule most worth defending.

### What leaking looks like

| Leaking into the core | Do this instead |
| --- | --- |
| "If co-working, require payment before confirm" | Payment policy on the resource type: charge on submit |
| "If workplace, hide prices" | A setting `pricing.enabled: false`, turned on by the product's preset |
| "If tenant is GreenDesk, allow 3-hour bookings" | A rule GreenDesk configures |
| A `member_plan` column on the core booking table | A custom field defined by the product's preset |
| "If the type is desk, skip approval" | Flow config on the Desk type: confirmation instant |
| Invoice logic inside the Booking module | The product's backend listens to `booking.completed` |

### Why it hurts

- Every product-specific branch must be respected by every future change, and they multiply.
- Behaviour hidden in code can only be changed by us, which breaks the "no code for new requirements" promise.
- The second product starts by untangling the first one's code instead of reusing the core.

### How we avoid it

1. **Name the behaviour, not the customer.** "Co-working needs up-front payment" becomes "payment timing is configurable".
2. **Presets carry the product.** The core only reads settings.
3. **Products live in their own repos and depend on the core, never the reverse.**
4. **Banned words, checked in the pipeline:** `coworking`, `co_working`, `workplace`, `office`, `member_plan` and customer names, anywhere except `seeds/`.
5. **Review question on every core change:** "Would this make sense for a clinic or a sports court?" If not, it belongs in a preset or a product.
6. **Three-customer rule:** one customer's request becomes a rule or an extension; a new core setting only when three customers need it.
7. **An unavoidable shortcut before a deadline** goes behind a named setting with a cleanup ticket, never behind a product or tenant check.

## Booking: pipeline, lifecycle, policies

A booking request is first **evaluated** by the pipeline, then **lives** in the lifecycle. Both are the same for every product and tenant; tenants change their behaviour through settings, rules and policies.

### The pipeline

Every request runs through the same seven steps, in this order:

| Step | Job | Tenant configures | Changes data? |
| --- | --- | --- | --- |
| 1. Validate request | Fields present and valid | Booking form, custom fields | No |
| 2. Check availability | Resource free for that time | Hours, blackouts, buffers, slots | No |
| 3. Eligibility rules | May this person book this resource? | Who may book what | No |
| 4. Limit rules | Duration, advance window, quotas | Limits | No |
| 5. Approval rules | Instant or needs approval? | Approval conditions | No |
| 6. Price | What it costs (after December) | Price plans, credits | No |
| 7. Save and start the lifecycle | Create the booking, run the submit transition, emit the event | — | **Yes** |

- **The order is how the engine evaluates, not how admins configure.** Admins edit each section independently, in any order.
- **Why it's fixed:** later steps depend on earlier ones, members get the most useful reason first, cheap checks run first, and results stay predictable.
- **Steps 1–6 only decide**, so they can run as a dry run: "would this booking be allowed?"
- **Every "no" names the setting or rule that stopped it**, shown to the member and tracked.
- **Payment is not a step.** It's a lifecycle policy (below).

### The lifecycle

Nine fixed statuses. Tenants never add statuses; their policies switch optional paths on or off. Tenants may rename the labels members see.

| Status | Kind | Meaning |
| --- | --- | --- |
| `awaiting_payment` | Optional | Waiting for payment; only when the payment policy needs it |
| `pending_approval` | Optional | Waiting for an approver; only when approval rules require it |
| `confirmed` | Main | Holds the slot |
| `checked_in` | Main | The member arrived |
| `completed` | End | Ended normally |
| `expired` | End | Payment failed or timed out |
| `rejected` | End | An approver rejected it |
| `cancelled` | End | Member or admin cancelled |
| `no_show` | End | No check-in within the window |

`submitted` is the entry point (pipeline step 7), not a stored status.

#### Allowed moves

| From | Move | To | Triggered by | What runs |
| --- | --- | --- | --- | --- |
| submitted | `require_payment` | awaiting_payment | Payment policy | Payment hold or charge |
| submitted, awaiting_payment | `require_approval`, `paid` | pending_approval | Approval rules | Approver notified |
| submitted, awaiting_payment, pending_approval | `confirm`, `paid`, `approve` | confirmed | System or approver | Confirmation, calendar update |
| awaiting_payment | `payment_failed`, timeout | expired | Payment provider or timer | Slot released |
| pending_approval | `reject` | rejected | Approver | Money released, member told why |
| awaiting_payment, pending_approval, confirmed | `cancel` | cancelled | Member or admin | Cancellation policy, refund if any |
| confirmed | `check_in` | checked_in | Member | Only inside the check-in window |
| confirmed | `no_show` | no_show | Timer | No-show policy: release, fee or strike |
| checked_in | `complete` | completed | Timer or check-out | Usage recorded; charge if pay-after-use |

Every move goes through one `transition()` function. It runs the rules and the payment hook, writes history, and emits exactly one event, so a booking can never reach an impossible state.

### Policies per resource type

Each resource type carries policies for confirmation, check-in, cancellation and payment. Example: [examples/flow-config.json](docs/examples/flow-config.json).

Each booking stores a copy of the policies it was made under. Changing settings never changes existing bookings.

#### Payment is a policy, not a step

The payment policy says **which transition takes the money**. Payment status is tracked separately from booking status: `unpaid`, `held`, `paid`, `refunded`. Example: [examples/payment-policy.json](docs/examples/payment-policy.json).

| Tenant wants | `chargeOn` | What happens |
| --- | --- | --- |
| Pay before review | `submit` | Hold at submit, capture on approve, release on reject |
| Pay after approval | `confirm` | Approved → awaiting payment → confirmed once paid |
| Pay after use | `complete` | Card saved at submit, charged for actual usage on completion |
| Monthly invoice | `none` + invoice | Each completed booking adds a line to the month's invoice |
| Free (December demo) | `none` | The payment hook does nothing |

A new payment timing is a new `chargeOn` option, never a change to the pipeline or the lifecycle.

## Rules

A rule is **scope + stage + condition + effect + priority**. Tenants combine predefined effects; they never write new ones. Example: [examples/rule.json](docs/examples/rule.json).

| Part | Values |
| --- | --- |
| Scope | Tenant, site, resource type or resource |
| Stage | `eligibility`, `limits`, `approval` (`pricing` later) |
| Condition (`when`) | JSONLogic over a fixed context: `booking`, `resource`, `user`, `user.groups`, `time`, `usage` |
| Effect | `deny`, `require_approval`, `max_duration`, `advance_window`, `quota`, `allowed_groups` |
| Priority | Higher runs first |

### How rules are evaluated

1. Load the published rules for the booking's scope, most general first: tenant → site → resource type → resource.
2. Build the context from the fixed keys above.
3. For the current stage, evaluate each rule's condition, highest priority first, and collect the effects.
4. Resolve conflicts: deny beats allow; ties go to the more specific scope.
5. Return a decision and a **trace** naming every rule that matched and what it did.

The same rules run in Python (the server's decision) and in the browser (admin previews). A shared file of example rules and expected results runs against both evaluators in the pipeline, so they can never disagree silently.

### Limits

- No loops, no external calls inside conditions, and a cap on rules per stage. Anything beyond that is an extension.
- AI-written rules return rule JSON, which is validated against the rule schema, previewed, and published by a person. The model never publishes.

## Configuration and custom fields

Everything a tenant configures (resource types, custom fields, policies, rules, notification templates) is data with a version number. Tenants never edit the live version directly.

### How a change goes live

1. **Draft:** the admin edits a copy; the live version keeps running.
2. **Validate:** the system checks it makes sense (min ≤ max, no unknown fields, no rule that blocks everything).
3. **Preview:** "test this rule against last week's bookings".
4. **Publish:** the draft becomes the new version; `config.published` records who, when and what.
5. **Roll back:** any earlier version can be republished as the newest.

- Saving a setting never silently rewrites stored data.
- Keys are permanent; labels can change freely.
- Bookings keep the config version they were made under.
- Drafts carry the version they're based on; publishing over a newer version fails with `STALE_VERSION`.

### Custom fields

| Layer | Answers | Tool |
| --- | --- | --- |
| Field definition | "Capacity is an integer, required, 1–200" | Our own format, edited in the console |
| Per-field validation | "Is `capacity: 250` valid?" | JSON Schema, generated from the definition |
| Cross-field rules | "With video conferencing, capacity must be at least 4" | JSONLogic `when` / `assert` |

We keep our own definition format because the console needs labels, order, help text and widgets, which JSON Schema lacks. It compiles to JSON Schema, which the browser and the server both validate against. JSON Schema runs first; cross-field rules only run if it passes. Errors come back per field. Example: [examples/field-definition.json](docs/examples/field-definition.json).

#### Field scope

Every field has a `scope`, set once when it's defined:

| Scope | Who sets the value | Where it's shown |
| --- | --- | --- |
| `resource` (default) | An admin, once per resource instance (e.g. a meeting room's TV type) | Read-only on the resource; never asked again at booking |
| `booking` | The member, on every booking (e.g. number of attendees) | The booking form |

A field's scope is part of its definition, like its type — changing it is a type-change-shaped edit (see below), not a free relabel.

#### Reference fields

A `reference` field's value is another resource's id. Its definition fixes which resource type that id must belong to (`FieldValidation.targetResourceTypeId`), chosen once when the field is defined — e.g. a `meeting_room`'s `primary_table` field is scoped to the `table` resource type. The console offers a picker of that type's resources wherever the value is set, instead of a raw id.

A reference is normally a `resource`-scoped field: an admin assigns the specific table once, when setting up the meeting room, the same as any other attribute. Nothing stops a `booking`-scoped reference (the member picks from a list at booking time), but that's the less common case.

A resource type can reference any other resource type, including itself. The core only stores the id and resolves it for display; it doesn't enforce lifecycle coupling (e.g. deleting a referenced resource doesn't cascade) — that stays a cross-product concern, same as [core-boundaries.md](#core-boundaries) describes for anything else a specific product needs.

#### Field types

| Type | Stored as | Validations |
| --- | --- | --- |
| text, long_text | string | required, minLength, maxLength, pattern |
| integer, number | number | required, min, max, multipleOf |
| boolean | boolean | required |
| date, datetime | ISO string | required |
| select | string | required, options |
| multi_select | array | required, options, minItems, maxItems |
| email, url, phone | string | required |
| reference | id | required, target type |
| file, multi_file | file id(s) | required, max size, MIME types |

When a definition is saved: min ≤ max, the pattern compiles and is length-capped, option values are unique, keys are snake_case and unique.

### Changing a field's type

A type change is a **data migration**, never a settings edit.

| Change | Kind | Conversion |
| --- | --- | --- |
| integer → number, wider ranges | Safe | None |
| file → multi_file, text → array, select → multi_select | Convertible | Wrap: `"a.pdf"` → `["a.pdf"]`, empty → `[]` |
| number or boolean → text | Convertible | Stringify |
| text → integer or date | Lossy | Parse; failures listed for manual fixing |
| array → single value | Lossy | Keep first or join; admin must confirm |
| Anything else | Not allowed | Create a new field instead |

The admin changes the type → a dry run converts every affected record without saving → the console shows the impact ("1,243 converted, 0 failures") → the admin confirms → a background migration runs in batches, saving old values to history → the new definition goes live only when the migration finishes.

**Minimum for December:** never rewrite data on save, the converter registry with dry run, and attribute history.

## Events

Every change in the core produces an event. Notifications, automations, webhooks, analytics and booking history **listen to events** instead of being called directly. That's what lets us add features without touching booking code.

### The outbox

A change and its event are saved in the **same database transaction**. A worker then delivers each event to its subscribers.

- **Nothing is lost:** if the change saved, the event exists; if the save failed, there is no event.
- **Subscribers can't break bookings:** a slow email server or broken webhook never blocks a booking; delivery retries in the background.
- **New subscribers need no core changes.**

### What every event carries

| Field | Example |
| --- | --- |
| Name | `booking.confirmed`, past tense: a fact, not a command |
| Tenant | The tenant's id |
| Subject | Booking 8841 on Room A |
| Actor | A user, or `system` for timers |
| Time | When it happened |
| Changes | Status `pending_approval` → `confirmed` |
| Config version | The flow config and rule set versions in force |

Example: [examples/event.json](docs/examples/event.json).

### Event catalogue

| Event | When | Typical subscribers |
| --- | --- | --- |
| `booking.requested` | A member submits a request | Analytics |
| `booking.denied` | A rule blocks the request (nothing is saved) | Analytics |
| `booking.awaiting_payment` | Payment needed | Payments, notifications |
| `booking.approval_requested` | Approval needed | Notification to approver |
| `booking.confirmed` | Booking confirmed | Email, calendar, analytics, webhooks |
| `booking.rejected` | Approver rejects | Email, analytics |
| `booking.expired` | Payment fails or times out | Email, analytics |
| `booking.checked_in` | Member checks in | Analytics |
| `booking.completed` | Booking ends | Analytics; invoicing later |
| `booking.cancelled` | Member or admin cancels | Email, analytics |
| `booking.no_show` | Check-in window passes | Email, strike counter, analytics |
| `resource.created`, `resource.updated` | Admin changes a resource | Audit, analytics |
| `config.published` | Admin publishes settings or rules | Audit, cache refresh |

### Ground rules

1. Events are never edited or deleted; a correction is a new event.
2. Subscribers must cope with receiving the same event twice.
3. Event names and fields are a contract: change them like an API, with a version.
4. To react to something, subscribe to its event. Never ask the Booking module to call you.

## API

Frontend writes the contract while building screens, Backend implements it. `contracts/openapi.yaml` is the only description of the API; the client, Zod schemas and mocks are generated from it.

### Conventions

| Topic | Rule | Example |
| --- | --- | --- |
| Base path | Versioned | `/api/v1/...` |
| Naming | Plural nouns, kebab-case paths, camelCase JSON | `GET /api/v1/resource-types`, `resourceTypeId` |
| IDs | UUIDv7 strings | `0193f4c2-...` |
| Time | ISO 8601 with offset; stored in UTC; sites return their timezone | `2026-12-15T14:00:00+07:00` |
| Lists | Cursor pagination | `?limit=50&cursor=...` → `data`, `nextCursor` |
| Lifecycle moves | Action endpoints; `status` is never writable | `POST /bookings/{id}/check-in`, `/cancel`, `/approve` |
| Auth | `Authorization: Bearer <JWT>` | — |
| Tenant | `X-Tenant-Id` header, checked against the user's memberships on every request; never from URL or body | — |
| Retries | `Idempotency-Key` header when creating bookings | — |
| Config edits | Carry `baseVersion`; stale → `STALE_VERSION` | — |
| Breaking changes | Additive changes are free; removals and renames need a new version | — |

Spectral checks these rules on every merge request.

### Errors

Every error uses problem details (RFC 9457) with a stable `code`. The frontend handles errors by `code`, never by message. Example: [examples/error-booking-denied.json](docs/examples/error-booking-denied.json).

| Code | Status | When |
| --- | --- | --- |
| `VALIDATION_FAILED` | 422 | Bad input; per-field `errors` |
| `BOOKING_DENIED` | 422 | A rule blocked it; `reasons` from the rule trace |
| `SLOT_TAKEN` | 409 | Someone else holds the slot |
| `INVALID_TRANSITION` | 409 | A move the lifecycle doesn't allow |
| `STALE_VERSION` | 409 | Config edit based on an old version |
| `UNAUTHENTICATED` | 401 | Missing, invalid or expired token |
| `FORBIDDEN` | 403 | Not allowed in this tenant |
| `NOT_FOUND` | 404 | — |

New codes are added here in the same merge request that introduces them.

### Contract workflow

1. A frontend engineer drafts a feature's endpoints in `openapi.yaml`, in the same merge request as the screens.
2. A backend engineer reviews within one working day: naming, feasibility, errors, anything the engine can't do.
3. Merging freezes the contract for that feature. Later changes need one frontend and one backend approval, plus the lead.
4. Backend implements it; Schemathesis fails the pipeline if responses don't match.
5. The feature switches from mock to real API; its scenario mocks move into tests.

Contracts go over one feature at a time, weekly at the latest. Backend starts in week one on work no screen defines: schema, double-booking guard, lifecycle, tenancy.

## Frontend guide

For anyone working in `web/apps/` or `web/packages/`. Shared rules live in the root [CLAUDE.md](CLAUDE.md); API rules in [api.md](#api); tracking in [analytics.md](#analytics-and-tracking).

### Stack

| Concern | Choice |
| --- | --- |
| Apps | React, TypeScript (strict), Vite, shadcn/ui |
| Server data | TanStack Query, only through Orval-generated hooks |
| Routing | TanStack Router: file-based routes, typed links and search params, loaders using TanStack Query |
| Forms | React Hook Form with two validators (below) |
| Rule previews | json-logic-js |
| Tracking, errors | PostHog and Sentry, set up by `app-kit` |
| Unit and component tests | Vitest, React Testing Library |
| End-to-end tests | Playwright |
| Component preview | Storybook (`web/storybook`), one instance for every package and app |

#### Two validators, two jobs

| Form | Fields known | Validator |
| --- | --- | --- |
| Fixed forms: create site, rule editor, standard booking fields | When we write the code | Zod via `zodResolver`; schemas generated by Orval from the contract |
| Custom-field forms: a phone booth's "Floor" and "Equipment" | At runtime, defined by the tenant | Ajv via `ajvResolver`, against the JSON Schema compiled from the field definitions |

Zod can't describe fields that only exist in a tenant's configuration. Ajv validates against the same JSON Schema the backend uses, so browser and server always agree. Router search params are validated with Zod.

### Code organisation

- **pnpm workspace:** rooted at `web/`; `apps/console` and `apps/member` depend on `@booking-core/*` packages via `workspace:*`.
- **Packages from day one:** `api-client`, `ui`, `custom-fields`, `rules-editor`, `booking-ui`, `app-kit`. Anything else starts in an app and moves to a package when a second consumer needs it.
- **No imports between apps.** If both apps need something, it moves to a package.
- **Each package exports through its `index.ts`.** Nothing imports another package's internals; packages never import from `web/apps/`.
- **Inside an app:** one folder per feature under `src/features/<feature>/`, with its components, hooks and tests together.
- **shadcn/ui components** live in `web/packages/ui`, are added with its CLI, and may be edited.

#### Rules for packages

Packages are what products install, so they are built as libraries:

- No routing, no login screens, no global app state. React and TanStack Query are peer dependencies.
- Customise through props, not copies: labels, render functions and slots (`renderResource`, `emptyState`).
- No product wording; default labels are generic ("Resource", "Booking") and overridable.
- ESM output with TypeScript types; each package has its own version and changelog (Changesets).
- If something is awkward to use from `apps/console` or `apps/member`, it will be awkward for every product.

#### `app-kit`

Every app starts through `app-kit`. It reads the runtime config, creates the query client, wires the JWT into the API client, initialises PostHog and Sentry with the app's name (`console` or `member`), and provides the top-level error boundary.

The query client disables `refetchOnWindowFocus` and retries, and treats a query as fresh for `staleTimeMinutes` (runtime config, default `DEFAULT_STALE_TIME_MINUTES` in `queryClient.ts`) before refetching it — screens that need fresher data after their own action call `queryClient.invalidateQueries(...)` explicitly rather than relying on a refetch-on-focus.

### UI rules

- No direct `fetch`; all server data goes through generated hooks.
- Handle errors by `code`.
- Every denial shows its reason from the rule trace.
- Every screen handles loading, empty and error states.
- Every new screen adds its tracking events in the same merge request ([analytics.md](#analytics-and-tracking)).

### Mocks

1. Edit `contracts/openapi.yaml` while building the screen.
2. Run `pnpm gen`: Orval regenerates hooks, Zod schemas and MSW mocks. Generated code is committed.
3. Add scenario handlers in `web/packages/api-client/src/scenarios/` where behaviour matters: `SLOT_TAKEN`, `BOOKING_DENIED` with reasons, slow responses. Each scenario's stateful logic lives in a plain, framework-free `*Operations.ts` module (e.g. `bookingsOperations.ts`); the MSW handlers in `*Store.ts` are a thin adapter over it, so the same logic also runs the shared mock server below.
4. Switch each feature from `mock` to `real` with the runtime `apiMode` setting and its per-feature overrides as the backend lands.

#### Shared mock server, for running both apps together

Each app's own MSW mocks are per-tab and reset on reload — fine solo, but console and member then can't see each other's data. `web/mock-server` runs the same scenario operations as one real local HTTP server instead, so a resource type created in console shows up in member, a booking made in member shows up in console's approvals and bookings list, and so on. It has no state of its own beyond those operations modules — it's the in-browser mock lifted out from behind MSW, not a second implementation.

Run it alongside both apps: `pnpm --filter mock-server dev` (serves `http://localhost:4000`, reset with `POST /__reset`). Both apps' `public/config.js` point at it by default (`apiMode: 'real'`). For solo work where running a third process isn't worth it, switch an app's `public/config.js` back to `apiMode: 'mock'` — each tab gets its own throwaway MSW data again, same as before.

### Running locally

From `web/`, run `pnpm --filter console dev` and `pnpm --filter member dev` natively, side by side, against the API, worker and database in Docker Compose. Node is pinned in `web/.nvmrc`, pnpm in `web/package.json`. Images and runtime config: [operations.md](#operations). Before that backend exists for a given feature, run `pnpm --filter mock-server dev` alongside them instead — see "Shared mock server" above.

Environment values are read at runtime from `window.__CONFIG__`, never from `import.meta.env`, so one image runs everywhere.

### Storybook

One Storybook instance (`web/storybook`) previews every component in `web/packages/*` and `web/apps/*` in isolation, without wiring it into a page or running a full app. Run it with `pnpm --filter storybook dev` (serves `http://localhost:6006`).

- A story lives next to the component it covers, as `<Component>.stories.tsx` — not in `web/storybook`, which holds only the Storybook config (`.storybook/main.ts`, `.storybook/preview.tsx`).
- `msw-storybook-addon` intercepts requests with the same scenario handlers apps use (`handlers` from `@booking-core/api-client`), reset before every story — so a story can exercise a real mutation (approve a booking, cancel it) and see it actually change, the same as in the app. Give a fixture the same id as a seeded record (see `bookingsOperations.ts`) when a story needs to act on it.
- `.storybook/preview.tsx` wraps every story in a `QueryClientProvider` and `TooltipProvider`, matching what `CoreAppProvider` does for a real app.
- See [decisions.md](#decision-log) (D-001) for why this is one instance instead of one per package.
- Add a component's story once it's built and confirmed, not while it's still taking shape — see step 4 of ["Testing: features first, tests before commit"](#testing-features-first-tests-before-commit) below.

### Testing: features first, tests before commit

Tests written while a feature is still taking shape usually encode the wrong behaviour and get thrown away. So:

1. **Build the feature.** Don't create or edit test files yet.
2. **Hand over for verification.** Tell the developer exactly what to check: screens, loading, empty and error states, and each error code the feature handles.
3. **The developer verifies** and confirms or asks for changes. Repeat until confirmed.
4. **Add or update Storybook stories** for any new or changed component, now that it's confirmed — not earlier, while it's still taking shape (same reasoning as tests before it). See [Storybook](#storybook) above.
5. **Propose test cases before committing:** a short list, each with a name, what it covers, and its type (unit, component, end-to-end). Prioritise user-visible behaviour, handled error codes, and edge cases found during verification. Skip layout, styling and shadcn/ui itself. Hold end-to-end tests until the flow they cover is mostly built — a screen built alone still gets unit and component tests now.
6. **The developer approves or edits the list.**
7. **Write and run the tests** with lint and type checks. If a test fails because the feature is wrong, fix the feature. If a test expects the wrong thing, flag it. Update existing tests only for behaviour the developer confirmed, and say so.
8. **Commit the feature, its stories and its tests together.**

The developer can ask for tests first when it helps, e.g. a tricky pure function.

#### What to test

| Area | Must have |
| --- | --- |
| Custom-field forms | Each field type renders and validates like the backend |
| Rule editor | Preview matches the shared rule examples |
| Errors | A clear message for each error code a screen handles |
| Key flows | Search → book → confirm; check in; cancel; approve |
| Demo | The seven demo steps, end to end with Playwright, before each rehearsal |

## Backend guide

For anyone working in `core/`. Shared rules live in the root [CLAUDE.md](CLAUDE.md); API rules in [api.md](#api); domain behaviour in [domain/](#booking-pipeline-lifecycle-policies).

### Structure

One Flask app in `core/api/`. Each core module is a package under `core/api/modules/` (tenancy, users, resources, availability, booking, rules, pricing, config, notifications, events). The worker lives in `core/api/worker/` and runs from the same image.

Each module has:

| File | Holds |
| --- | --- |
| `api.py` | Flask blueprint: routes only, no business logic |
| `service.py` | The public interface other modules may call |
| `models.py` | SQLAlchemy models, private to the module |
| `schemas.py` | Pydantic request and response models, mirroring the contract |
| `events.py` | Events the module emits |

### Rules

- A module may import another module's `service.py` only. import-linter enforces it.
- A route parses input, calls **one** service function, and returns a response model.
- A service function runs in one transaction; any change writes its events to the outbox in that same transaction.
- Booking status changes only through `transition()`.
- Keep functions small and single-purpose; tests ship in the same merge request.
- Migrations: Alembic, run as a separate deploy step, never at app start. Backward compatible for one release: add, deploy, remove later.
- Logs: JSON to standard output, with request id and tenant id on every line.

### Libraries

| Concern | Choice |
| --- | --- |
| Database | SQLAlchemy 2, Alembic |
| Validation | Pydantic v2; `jsonschema` for custom fields |
| Rules | A JSONLogic evaluator |
| Auth | PyJWT |
| Contract checks | Schemathesis |
| Boundaries | import-linter |
| Lint and format | ruff |
| Tests | pytest |
| Serving | Gunicorn behind Caddy |

### Data and tenancy

- Every table has `tenant_id`, filtered by row-level security policies. Example: [examples/sql/tenant-isolation.sql](docs/examples/sql/tenant-isolation.sql).
- After verifying the JWT and the user's membership in the requested tenant, the API sets the tenant for the transaction (`SET LOCAL app.tenant_id`).
- The app connects as a role that does **not** own the tables; owners bypass row-level security unless it's forced.
- Double bookings are impossible: an exclusion constraint on resource and time range rejects the second of two racing requests, and the API returns `SLOT_TAKEN`. Example: [examples/sql/no-double-booking.sql](docs/examples/sql/no-double-booking.sql). Shared-capacity spaces use a row-locked counter instead.
- IDs are UUIDv7. Timestamps are `timestamptz`.

| Table | Holds |
| --- | --- |
| `resource_types` | Field definitions (`field_defs`), policies (`flow_config`), `version` |
| `resources` | Custom field values in `attributes` (JSONB, GIN index), `definition_version` |
| `config_versions` | Every draft and published version of settings and rules |
| `bookings` | `during` (time range), `status`, `payment_status`, `applied_config` |
| `booking_events` | Booking history: from, to, actor, reason |
| `attribute_history` | Previous custom field values |
| `outbox` | Events waiting for delivery |
| `scheduled_jobs` | Timers: no-shows, approval timeouts, payment-hold expiry |

### Auth

Users sign in through our existing auth service, which issues JWTs. The core never handles passwords.

- **Verify every token:** signature, `exp`, `iss`, `aud`. Prefer asymmetric keys (RS256 or ES256) from the auth service's JWKS endpoint. With a shared secret (HS256), keep it in the server's `.env` and plan a move to asymmetric keys.
- **Map the user:** `sub` maps to a core user, created on first sight from the token's claims.
- **Tenant and role come from the core:** the user's membership in the tenant named by `X-Tenant-Id`. One person can belong to several tenants.
- **Roles per tenant:** `owner`, `admin`, `staff`, `member`, `guest`; optionally scoped to a site.
- **Behind an adapter:** token verification sits behind one `AuthAdapter` class, so changing providers touches one place.
- **Service tokens** for product backends (after December) are JWTs with a `scope` claim.

### Engine

#### `transition()`

Looks up the move in the lifecycle table ([domain/booking.md](#booking-pipeline-lifecycle-policies)) and raises `INVALID_TRANSITION` if it's not allowed. Then it runs the hooks for the target status (rules, payment, check-in window), which may deny with reasons. Finally it updates the status, writes a `booking_events` row and adds the event to the outbox, all in the request's transaction. The payment hook has one implementation for December: `NoPayment`.

#### Rules

Evaluation follows [domain/rules.md](#rules). Published rule sets are cached per tenant and refreshed on `config.published`.

#### Worker

- **Outbox delivery:** picks up undelivered events with `FOR UPDATE SKIP LOCKED`, hands each to its subscribers, and marks it delivered. Failures retry with growing delays and are parked with an alert after a set number of attempts.
- **Timers:** runs due `scheduled_jobs`, each through `transition()`.
- **Duplicates:** each subscriber records processed event ids and skips repeats.

### Testing

Tests are written together with the code, in the same merge request. Backend functions are small and fully specified, so tests are cheap and catch the costliest bugs early. Agents write them as part of the task.

| Area | Must have |
| --- | --- |
| Lifecycle | Every allowed move works; every other move raises `INVALID_TRANSITION`; each move writes history and one event |
| Rules | The shared example file passes; deny beats allow; traces are correct |
| Double booking | Two parallel requests for one slot: exactly one succeeds (real PostgreSQL) |
| Tenancy | Tenant A can't read or change tenant B's data through any endpoint |
| Auth | Expired, wrongly signed and wrong-audience tokens are rejected; non-members get `FORBIDDEN` |
| Time | Daylight-saving changes and midnight in the site's timezone |
| Contract | Responses match `openapi.yaml` (Schemathesis) |
| Worker | A duplicate event is processed once; failures retry |
| Seeds | Every seed tenant applies through the public API |

## Analytics and tracking

We build product and UX analytics first, to answer the boss's questions: how many people use our products, how long they stay, whether they like it, and what blocks them. Customer-facing space analytics (utilisation, occupancy, no-shows) comes later, from the same events.

### What we measure

| Question | Measure | How we capture it |
| --- | --- | --- |
| How many users? | Daily, weekly, monthly active users by tenant, role and app; new vs returning | Every tracked event carries user, tenant, role and app |
| How long and how often? | Session length, sessions per week, retention after 1, 4 and 12 weeks | Session tracking; weekly retention groups |
| Do they like it? | A 1–5 score after key tasks, a quarterly recommend score, retention | In-app surveys, at most once every few weeks per person |
| What blocks them? | Funnel drop-off, searches with no results, rule denials, errors, time to finish | Funnels, error tracking, session replay, monthly interviews |

### Funnels

1. **Member booking:** open app → search → pick a resource → submit → confirmed.
2. **Tenant setup:** create site → add resource type → add resources → first member booking (an activated tenant).
3. **Rule change:** open rules → edit → preview → publish.

### How we track

- **Tools:** PostHog (events, funnels, retention, replay, surveys) and Sentry (errors), both hosted.
- **Two sources:** apps send screen actions; the worker forwards core events from the server. Business numbers come from server events, so ad blockers can't skew them.
- **Identity:** identify the user after login. Every event carries `tenantId`, `role` and `app` (`console` or `member`).
- **Naming:** screen events are `object_action`, snake_case, past tense (`booking_search_submitted`). Core events keep their dotted names (`booking.confirmed`).
- **Privacy:** session replay masks all inputs and member names and emails; no personal data in event properties.
- **Separate projects** for local, staging and production.
- **Monthly review:** 30 minutes on the numbers plus three to five short user interviews.
- **Every new screen** adds its events to the tracking plan in the same merge request.

### Tracking plan

| Event | Sent when | Properties | Funnel |
| --- | --- | --- | --- |
| `booking_search_submitted` | Member searches | siteId, resourceTypeId, date, resultsCount | Member booking |
| `resource_selected` | Member opens a result | resourceTypeId, position | Member booking |
| `booking_submitted` | Member presses Book | resourceTypeId, durationMinutes | Member booking |
| `booking.confirmed` (server) | Lifecycle confirms | path, minutesSinceSearch | Member booking |
| `booking.denied` (server) | A rule blocks | ruleIds | What blocks them |
| `resource_type_created` | Admin saves a type | fieldCount | Tenant setup |
| `resource_created` | Admin adds a resource to a type | resourceTypeId | Tenant setup |
| `resource_type_flow_config_updated` | Admin saves a type's flow config | resourceTypeId, confirmation | Tenant setup |
| `rule_published` | Admin publishes a rule | stage, effect, previewUsed | Rule change |
| `survey_answered` | Member answers the post-booking survey | score | Do they like it |
| `my_bookings_viewed` | Member opens "My bookings" | resultsCount | — |

## Operations

For anyone working on Docker, the pipeline, the demo server or deploys. The files themselves live in `infra/` and `.gitlab-ci.yml`.

### Environments

| Environment | Where | Data | Deployed |
| --- | --- | --- | --- |
| Local | Laptops: API, worker, database in Compose; apps run natively | Seed data, reset at will | By hand |
| Staging (demo) | Our internal physical server, by IP address; Docker Compose, Caddy | Seeded demo tenants | Every merge to `master` |
| Production | AWS or Azure | Real tenants | Tagged releases |

**Demo server containers:** `caddy`, `console`, `member`, `api`, `worker`, `postgres`, and a GitLab Runner. **Outside services:** the existing auth service, PostHog, Sentry, and our GitLab (code, pipeline, container and package registries).

### Images

| Image | Built from | Notes |
| --- | --- | --- |
| `api` | `core/api/` | The worker runs from the same image with a different command |
| `console`, `member` | `infra/web/Dockerfile` with `APP=console` or `APP=member` | One recipe, one nginx config, one runtime config script for both |

- Images are tagged with the commit SHA and pushed to the GitLab container registry.
- Frontend images read environment values at container start (`infra/web/40-runtime-config.sh` writes `config.js`), so one image runs in every environment.
- The demo server is on the internal network and reached by its IP address. Caddy (`infra/Caddyfile`) serves the member app on port 3000 and the console on port 3001, and each port forwards `/api/*` to the API. The browser talks to one address per app, so there's no cross-origin setup and `API_URL` stays empty.
- It runs on plain HTTP inside the office network. Before anyone reaches the server from outside, switch to domain names, which gives automatic HTTPS.

### Cloud-ready rules

- All configuration comes from environment variables.
- Containers keep no state; uploaded files (later) go to object storage.
- Logs go to standard output.
- Migrations run as a separate step.

| Piece | Demo server | AWS | Azure |
| --- | --- | --- | --- |
| HTTPS and routing | Caddy (HTTP by IP for now) | Load balancer + Certificate Manager | Application Gateway or Front Door |
| Apps, API, worker | Docker Compose | ECS on Fargate | Container Apps |
| Database | PostgreSQL container | RDS for PostgreSQL | Azure Database for PostgreSQL |
| Images | GitLab container registry | GitLab or ECR | GitLab or Azure Container Registry |
| Secrets | `.env` on the server | Secrets Manager | Key Vault |

### Pipeline

Defined in `.gitlab-ci.yml`.

**On every merge request:**

1. Lint and types: ruff; Biome and `tsc`.
2. Contract: Spectral lints `openapi.yaml`; the generated client must match what's committed.
3. Boundaries: import-linter; Biome import rules (apps use only package entry points, apps don't import each other, packages don't import apps); banned product words outside `seeds/`.
4. Tests: backend against real PostgreSQL; frontend unit and component tests.
5. API and seeds: Schemathesis against the running API; every seed tenant applies cleanly.
6. All three images build.

A merge request can't be merged until the pipeline passes.

**On merge to `master`:** images are pushed, then the GitLab Runner on the demo server pulls them, runs migrations as a one-off container, restarts the services and checks `/api/healthz`. A runner on the server means no SSH access from outside.

**Rollback:** re-run the deploy job from the previous commit's pipeline.

### Secrets

- Pipeline secrets are masked, protected GitLab CI/CD variables.
- Server secrets live in `/srv/booking-core/.env`, readable only by the deploy user.
- Never in git.

### Backups and runbooks

- The database is backed up nightly and copied off the server. A restore is tested before the demo.
- Every manual change to the server is written down in `docs/runbooks/` first. Each runbook is a future script.
