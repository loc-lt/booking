# Frontend guide

For anyone working in `apps/` or `packages/`. Shared rules live in the root [CLAUDE.md](../CLAUDE.md); API rules in [api.md](api.md); tracking in [analytics.md](analytics.md).

## Stack

| Concern | Choice |
| --- | --- |
| Apps | React, TypeScript (strict), Vite, shadcn/ui |
| Server data | TanStack Query, only through Orval-generated hooks |
| Routing | TanStack Router: file-based routes, typed links and search params, loaders using TanStack Query |
| Forms | React Hook Form with two validators (below) |
| Rule previews | json-logic-js |
| Tracking, errors | PostHog and Sentry, set up by `app-kit` |
| Unit and component tests | Vitest, React Testing Library |
| End-to-end tests | Playwright |

### Two validators, two jobs

| Form | Fields known | Validator |
| --- | --- | --- |
| Fixed forms: create site, rule editor, standard booking fields | When we write the code | Zod via `zodResolver`; schemas generated by Orval from the contract |
| Custom-field forms: a phone booth's "Floor" and "Equipment" | At runtime, defined by the tenant | Ajv via `ajvResolver`, against the JSON Schema compiled from the field definitions |

Zod can't describe fields that only exist in a tenant's configuration. Ajv validates against the same JSON Schema the backend uses, so browser and server always agree. Router search params are validated with Zod.

## Code organisation

- **pnpm workspace:** `apps/console` and `apps/member` depend on `@booking-core/*` packages via `workspace:*`.
- **Packages from day one:** `api-client`, `ui`, `custom-fields`, `rules-editor`, `booking-ui`, `app-kit`. Anything else starts in an app and moves to a package when a second consumer needs it.
- **No imports between apps.** If both apps need something, it moves to a package.
- **Each package exports through its `index.ts`.** Nothing imports another package's internals; packages never import from `apps/`.
- **Inside an app:** one folder per feature under `src/features/<feature>/`, with its components, hooks and tests together.
- **shadcn/ui components** live in `packages/ui`, are added with its CLI, and may be edited.

### Rules for packages

Packages are what products install, so they are built as libraries:

- No routing, no login screens, no global app state. React and TanStack Query are peer dependencies.
- Customise through props, not copies: labels, render functions and slots (`renderResource`, `emptyState`).
- No product wording; default labels are generic ("Resource", "Booking") and overridable.
- ESM output with TypeScript types; each package has its own version and changelog (Changesets).
- If something is awkward to use from `apps/console` or `apps/member`, it will be awkward for every product.

### `app-kit`

Every app starts through `app-kit`. It reads the runtime config, creates the query client, wires the JWT into the API client, initialises PostHog and Sentry with the app's name (`console` or `member`), and provides the top-level error boundary.

## UI rules

- No direct `fetch`; all server data goes through generated hooks.
- Handle errors by `code`.
- Every denial shows its reason from the rule trace.
- Every screen handles loading, empty and error states.
- Every new screen adds its tracking events in the same merge request ([analytics.md](analytics.md)).

## Mocks

1. Edit `contracts/openapi.yaml` while building the screen.
2. Run `pnpm gen`: Orval regenerates hooks, Zod schemas and MSW mocks. Generated code is committed.
3. Add scenario handlers in `packages/api-client/src/scenarios/` where behaviour matters: `SLOT_TAKEN`, `BOOKING_DENIED` with reasons, slow responses.
4. Switch each feature from `mock` to `real` with the runtime `apiMode` setting and its per-feature overrides as the backend lands.

## Running locally

Run `pnpm --filter console dev` and `pnpm --filter member dev` natively, side by side, against the API, worker and database in Docker Compose. Node is pinned in `.nvmrc`, pnpm in `package.json`. Images and runtime config: [operations.md](operations.md).

Environment values are read at runtime from `window.__CONFIG__`, never from `import.meta.env`, so one image runs everywhere.

## Testing: features first, tests before commit

Tests written while a feature is still taking shape usually encode the wrong behaviour and get thrown away. So:

1. **Build the feature.** Don't create or edit test files yet.
2. **Hand over for verification.** Tell the developer exactly what to check: screens, loading, empty and error states, and each error code the feature handles.
3. **The developer verifies** and confirms or asks for changes. Repeat until confirmed.
4. **Propose test cases before committing:** a short list, each with a name, what it covers, and its type (unit, component, end-to-end). Prioritise user-visible behaviour, handled error codes, and edge cases found during verification. Skip layout, styling and shadcn/ui itself.
5. **The developer approves or edits the list.**
6. **Write and run the tests** with lint and type checks. If a test fails because the feature is wrong, fix the feature. If a test expects the wrong thing, flag it. Update existing tests only for behaviour the developer confirmed, and say so.
7. **Commit the feature and its tests together.**

The developer can ask for tests first when it helps, e.g. a tricky pure function.

### What to test

| Area | Must have |
| --- | --- |
| Custom-field forms | Each field type renders and validates like the backend |
| Rule editor | Preview matches the shared rule examples |
| Errors | A clear message for each error code a screen handles |
| Key flows | Search → book → confirm; check in; cancel; approve |
| Demo | The seven demo steps, end to end with Playwright, before each rehearsal |
